## Work-scoped admission

Actual original Work may add optional `software_admission` to its exact
`delegate-processing --selection FILE` selection. Omission grants none. It is
genuine prospective **software** authority under Work's user delegation, not
native Branch consent or independent QA/human acceptance. The selection freezes
reusable, exact task scopes. It does not ask persistent native Branch to apply
each new package.

The following illustrates the shape, with deliberately non-operational values:

```json
{
  "authority": "actual Work authority, outcome, boundaries and why",
  "max_packages": 8,
  "scopes": {
    "EXACT-SELECTED-BOARD-TOPIC": {
      "submitters": ["ACTUAL-AUTHORIZED-SUBMITTER"],
      "package_prefix": "ACTUAL-NEW-PACKAGE-NAMESPACE-",
      "evidence": "actual scope/resource delegation evidence, distinct from old holds",
      "task_scopes": {
        "qa-execution": {
          "cwd": "/ACTUAL/ADMITTED/WORKTREE",
          "read_roots": ["/ACTUAL/ADMITTED/WORKTREE"],
          "write_roots": [],
          "procedure": "/ACTUAL/ADMITTED/PROCEDURE.md",
          "resource_evidence": "actual resource authority and limits"
        }
      }
    }
  }
}
```

Each task must already be in the processing task allowlist, be a scoped Branch
or QA task, and fit its original configured roots/network/authority. Ordinary
effect operands, if applicable, remain subject to their existing exact
procedure/resource/independent-acceptor contracts. This extension does not
activate the ordinary effect adapter. It does not widen a task or authorize CI,
Stage, ref effects, canonical publication or independent acceptance.

A genuinely new addressed Board source selects that exact topic. Its original
`ref` supplies the package; its original author must be an authorized submitter.
It must be received after the selection's runtime event boundary and posted
after its original per-role future frontier. Retained sources, old same-name
packages, held inputs and existing admissions/jobs cannot inherit it. Message
text supplies no paths, resources or receipt. Processing applies the issuer's
frozen scope before fresh classification; optional explicit recovery of a lost
local reply is `processing-admit-source CAPABILITY EVENT`. Both paths use the
same operation. Repeating an unchanged successful operation returns its prior
admission. It neither reruns a job nor manufactures an accepted receipt.

The admission row names the software actor, carries issuer/capability/source
hash/scope/evidence, and leaves `accepted` null. Its separate attribution in
`processing_admissions` remains in the existing journal and processing-status.
Only that source or an exact same-package descendant may use the software
admission. Existing native admissions keep their original path. Enrollment,
revocations, role holds, unknown effects and original custody are unchanged.
Thus a scoped package may still be unreservable because its actual resource or
effect hold is unresolved. A new namespace alone does not release that hold.

## Control interpretation and real return obligations

The fresh Luna input excludes package-required tasks when the source package is
null. It still offers honest control/unresolved choices. Commit uses the same
route set, preserves source/package identity, and cannot create admission.
This fixes an impossible choice offered to the null-package QA control in 207;
it is not evidence that a future model chooses the right remaining option.

Control wire status is now an explicit enum: `DONE`, `PARTIAL`, `FAILED`,
`UNKNOWN`. Actual meaning goes in summary and the full resolution receipt.
Complete bounded interpretation is distinct from native receipt, subsequent
consumer processing and acceptance. Successful actual collection, source and
result bindings, observed worker identity and complete no-tool metadata remain
required. A partial/failed/unknown return does not become success.

Applying one control interpretation atomically appends its attributed
resolution **and one whole durable Work return**, with the original source,
actual worker result and resolution. The response is a child source in the
same journal. It needs its own fresh classifier and a selected read-only Work
proposer consumer. No such consumer is an explicit dependency; the local
transaction rolls back without rewriting the worker. Source completion cannot
precede that child's processing and all existing downstream/hold checks.
There is no external post, fake native receive or duplicate service here.

## Recovering old free-text control status without replay

The old schema/prompt permitted prose or `CONTROL`, while disposition required
literal `DONE`. The original 207 workers really ended/collected0; that is not
the same as their control being accepted or the QA source being processed.
Those original results must not be relabelled, rerun or retroactively credited.

Actual Work can inspect `processing-source CAPABILITY EVENT`, which returns the
exact original control attempt/result as well as source, resolution and return.
For a subsequent deliberately selected recovery capability, keep the existing
`recover_controls: {EVENT: ORIGINAL_ATTEMPT}` binding and optionally add:

```json
{
  "control_recognitions": {
    "EXACT-RETAINED-EVENT": {
      "attempt": "EXACT-ORIGINAL-ATTEMPT",
      "result_hash": "ACTUAL-DIGEST-OF-THE-WHOLE-ORIGINAL-RESULT",
      "reason": "Work's actual interpretation of this exact old status and why",
      "evidence": ["actual full-return/source/evidence references"]
    }
  }
}
```

The hash uses the runtime's canonical `contracts.digest`, not a file hash or
hash of a summary. Recognition requires the same explicit recovery event and
attempt, complete structured original decision and meaningful summary. Typed
PARTIAL/FAILED/UNKNOWN and null decisions are refused even with recognition.
`processing-apply-control CAPABILITY EVENT --attempt ORIGINAL_ATTEMPT` consumes
that exact collected return; normal source/collector/tool/numeric-END checks
still apply. The resolution proof preserves the recognition and raw result
hash. Work's new scoped recognition supplies neither native owner consent nor
old-effect clearance. It leaves every unresolved receipt obligation in place.

## Operation, interruption and remaining work

Use only the real issuer's existing context and original configuration/journal.
Do not set identity, account/profile, HOME or CODEX_HOME to invoke commands.
Prepare fresh processing-basis, exact selection and preserve its returned ID.
Run the original bounded `processing-run`, preserve its terminal/controller,
collect that SAME original numeric END, read processing-status and status,
release with the actual parent collection receipt, then explicitly revoke.
Interrupted controllers/unknown children stay with their original collector;
no restart, takeover or blind source/effect replay is provided. Revocation
stops authorization for new work; source duties and new schema rows remain.

For rollback, collect/drain and revoke the capability; do not reset the journal
or re-enable old grants. A prior source version is not a data downgrade path
for the new software admissions/control returns. Hold their affected sources
and use forward recovery under a deliberate current selection. The public
pool continues to govern future allocation/admission atomically; these changes
neither edit the pool nor move started contexts.

Three distinct gaps return to actual Work. First, selected RFQ Reviews needs a
compatible real continuing reviewer-context/material/history/collection and
return interface, not the current disposable app-server or an intake proposal.
Second, the adapter still has one-hour authority/start/cumulative bounds and
explicit original-collector release; no continuing process authority/recovery
owner has been operationally bound here. Third, cleanup is disabled in this
adapter and inherited retirement conserves cumulative source/results rows;
sustainable same-journal conservation/retirement and exact shared effect-owner
proof are unfinished. No new journal, global method/route change or blind
deletion is supplied to hide those gaps.

Actual old-effect owners retain the historical unknowns. Human/external
acceptance is independent. These are genuine dependencies; they do not revoke
Work's existing authorization for eligible prospective software work. Actual
Work decides a bounded partial-use disposition versus further separately
bounded construction/provider pairing. No new user-permission or whole-RFQ
review gate is imposed by this source.
