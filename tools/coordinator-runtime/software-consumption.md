# Prospective software consumers (partial Decision27 contribution)

This contribution implements prospective delegation and actual software handoff
settlement. It does not complete the four-role cutover. Selected Reviews execution
still uses its owner path; Branch/QA external effects still require their actual
owner evidence. No effect flag, review binding or pending native duty is changed.

`software_delegation` selects `{grantor,authority,boundary:"new-journal-only"}`.
The grantor must be the configured actual Work identity, operating under the
supplied user authority. `enroll-software ROLE --authority EXACT_REFERENCE`
requires that actual grantor context, a new unused journal/role, an existing
managed role membership and a separate service actor. It records Work as issuer
and the genuine role owner separately. It grants the existing scoped delivery
and completion capabilities plus exact task/configuration hashes. No native
owner issuance or owner full-read is inferred. Old `enroll` behavior remains.
`revoke-software ROLE --grant EXACT_ID` lets that same actual Work issuer revoke
only its prospective software capability and stop new intake; pending work and
all old native authority/receipt/custody remain owned. Stopping/collecting a live
service and disposing existing work still belong to their actual collectors.

A task may select `software_handoffs`, mapping an enrolled recipient role to
explicit receiving task IDs. These must also be within its ordinary handoff and
the receiving role's task allowlists. Work/results alone can use this path;
questions, alerts and unresolved effects keep their actual exception routes.
Root remains external. Cross-board automatic consumption is refused.

The launcher binds each new instance to its exact grant, task and package
admission used to scope that instance. The final operation guard rechecks that
proof before process creation (including after a pool-lock wait), thread creation,
every initial turn and supported same-session continuation. Changed admission,
missing proof/checker or revocation refuses; a later processing receipt is not a
substitute for current launch authority. The sender must have
collected successful local processing, complete tool metadata and known effects;
file tasks also retain their full readiness and preimage/publication checks.
This does not establish independent semantic acceptance.

After an actual addressed board post, a durable board receiver intent binds the
immutable source, receiver grant and exact event. A crash before local ingest
retries that intent; it does not launch the business operation again. Published
internal responses and their exact result handoffs share one receiver event.
Both outboxes keep their original source and independent receipts. No aggregate
claim of atomic publication across databases follows.
In this new epoch the normal board scanner excludes the service's own delivery
posts; the exact receiver intent handles them. It cannot independently dispatch
a duplicate cross-role work instance while that intent awaits collection.

Actual fresh classification plus queued responsibility permits notice receipt
and pickup. Enqueue, classification and ACK never establish processing. The
receiving job must contain that exact frozen event and actually finish its own
bounded local work with numeric process END, collected result, complete tool
metadata, known effects and no holds. Only then does the service settle the
addressed handoff, recording the real worker, collector, result hash, effects and
grantor. Receiving downstream duties remain independently owned. Original source
processing still waits for the existing descendant/outbox barriers.

New clean software callbacks do not create independent native receive duties.
Any existing requirement, unknown/inflight control or foreign transport attempt
remains intact and can still mask processing/delivery satisfaction. Own-result
callbacks and both cross-role receipt checks refuse ambiguous/sending
notices and transport-started rows without changing their custody or replaying.
Normal reachability of the inherited mixed-transport state remains unestablished;
this protection does not claim an actual transport loss.
Original grants, collectors, authority epochs and source/custody are never migrated here.
Changing an existing journal's configuration still refuses. A new journal is
not automatic migration or release of old scoped resource holds; those require
parent-owned conservation and explicit resource-owner disposition before use.

Do not enable this as a complete rollout: the supported capability-compatible
opaque `gpt-xhigh`/Source selected-review instance and delegated Branch/QA effect
proof remain unimplemented. The public CRW semantic contract specifies `agents`
manual launches; this runtime's app-server adapter disables delegation. No
substitute binding or hypothetical executable is supplied. Work must collect
that material interface question together with this partial source return.

Contained boundary verification uses `tests/test_coherent_cutover.py` with
`COORDINATOR_COHERENT_FIXTURES` naming an owned absolute retained witness directory.
It does not reassign HOME or session/account identity. Policy, collection and
membership fixtures are synthetic, with owned SQLite and Python subprocesses.
The inherited `test_software_consumption.py` setup requires HOME substitution;
do not run that setup under the no-HOME bound. Its prior adverse evidence remains
with the original custodian. These fixtures do not establish genuine review,
ref operations, CI, semantic acceptance or live adoption.
Retain queued/output material through actual processing +24h AND every source,
consumer, outbox, resource, recovery and effect-uncertainty hold. No cleanup.
