# Continuous point integration

This source capability retains the existing file consumers, seven Work duties,
review/QA/CI/acceptance/risk gates and original collectors. It establishes no live
adoption, policy ownership, model efficacy, latency or receiving qualification.

## Held proposer and scoped file coordination

An old held Work proposer with no local scope continues to fence incoming
same-role material. Collected numeric END, PARTIAL, model DONE, a read-only task
name or an absent scope do not remove that fence. No scope is invented for it.

The actual Work owner can separately select `work-read-closure-basis JOB --token
TOKEN` and `fence-work-proposer JOB --token TOKEN --receipt FILE`. Both retain
the ordinary original Work authority checks, or accept `--management FILE`
through the existing current, exact, operation-local management protocol.
Management must name the exact proposer job, token, related event IDs and source
roles, with its genuine current authority/purpose, configuration/release/original
grant binding and expiry. Future-intake processing authority alone is insufficient;
these commands neither select processing nor revive original grants. Record
acquisition itself needs independently authorized access. Old integrator routes
remain integrator-only.

The basis requires held Work/proposer, no local scope, effects=none, no pending
recovery request or publication record, and an original frozen read-only/no-effect,
nonnetworked nonnative task with no write roots or routine publication. Every
related attempt, including diagnoses, must have genuine begun numeric END and
collection; the active original must be a task. The basis includes the unchanged
job and exact attempt collection/semantic/capture/error metadata plus the frozen
policy digest and all original controller identities. It reads no result or
capture body. Partial semantics and incomplete captures remain admissible *debt*,
not success. A retained recovery owner is permitted only in
`awaiting-disposition` or `owner-deferred`, with all related attempts collected.
That custodian is included among the controllers requiring closure evidence;
its identity, recovery state and duties remain unchanged. Active recovery is
not bypassed, and pending requests must receive their own lawful disposition.

The receipt has exactly `basis`, `reason` and `controllers`. Each controller
entry has exactly `controller`, `collector`, integer `end`, `collected:true`,
`writers_closed:true` and a nonempty bounded `evidence` list. The actual original
collectors must supply authentic whole controller, descendant and launch-capable
writer closure facts. Numeric task END does not supply them. These are attributed
owner assertions; software validates their binding, not their external truth.
Unavailable closure/authority facts remain explicit dependencies. Never fabricate
them or acquire excluded captures to fill the receipt.

Recording the receipt permanently refuses further launch, begin, callback,
finish or recovery execution of that exact predecessor through the existing
execution-open gate. It changes no old job/attempt/result/source/queue/outbox,
effect, consumer, custody, privacy or retention row. It does **not** change
`execution_complete`, release capacity/resources, complete processing, accept a
return or authorize old-job replay. All original custodians and duties remain.

An anchored, nonempty **file read** packet for a selected read-only,
nonnetworked, no-effect Work proposer may coexist with such a fence. A Work
integrator may also use it for an anchored known file scope under its existing
`owner-reconcile`, `workspace-write`, nonnetworked, nonnative routine-completion
authority. Its reads and writes must all be file points. A closed, permanently
execution-fenced nonwriting predecessor has no future conflicting read, even
though its original read scope remains unknown and its semantic duties endure.
This grants no scope, write roots, publication rights or acceptance. Proposer
writes, discovery, native points and other roles/phases retain their exclusions.
Each blocking predecessor needs its own exact receipt. Phase/shared limits still
count both held jobs; native busy checks, ordinary resource leases, known-scope
conflicts and ordinary source/member/admission gates remain in force. Reservation
records the exact fences in its local scope and launch revalidates them, the
frozen old metadata and current incoming task authority. Publication rechecks
the same dependencies before effects. A changed basis
refuses; it never reinterprets old debt or stamps a new revision on an old read.
Stale incoming versions still require the selected reconciliation method, and
later writing/integration/publication requires its genuine rights and ordinary
acceptance, including all seven joined consumer receipts. Cleanup still requires
actual whole-processing completion +24h and every hold. This capability supplies
no live admission, controller closure or rollout acceptance credit.

A controller selects `local_integration` explicitly in configuration. Existing
unselected journals/tasks retain their historical contracts. The supported
current-configuration draft accepts it as an explicit
`prospective_scope_selection.local_integration` option; every affected task must
be in the prospective task selection. It cannot change task effects, execution
admission, owners, roots, routes or canonical targets. Actual Work must select
current genuine point/resource/owner bindings and routine decision authority
before deployment. No example here is an operating configuration.

Use stable object keys or unique array field/value selectors, never array/line
indices. A point can bind multiple JSON consumer locations. `line` and
`incarnation` are genuine controller bindings, not model ownership claims.
Relevant relation sets, absence predicates and shared invariants are separate
read points. Select all actual dependencies; software does not discover hidden
semantic invariants from JSON leaves. Writable fields bound service changes;
unknown fields, protected ownership/identity fields and prior array members
remain conserved. Reassignment/acceptance needs separate real authority, not a
local model statement. Main and Cloud/PR1230 require distinct genuine bindings.

Scalar and list points use an explicit `writable: ["$value"]` for whole-value
changes. An empty writable list permits no change. Value types stay fixed;
changing a schema needs a separate authority decision. Prior list members,
including duplicates, survive with their JSON types recursively intact. A boolean
member cannot be spent as an integer (including inside arrays/objects); matching
consumes one occurrence, and genuinely new members may still append. The same
typed comparison guards protected views, write-sets and current-byte reuse.
Object field rights also conserve presence: an absent unselected or protected
field cannot be created as JSON null. Explicit null remains valid in selected
ordinary fields and neutral/proposal additions within their actual rights.
File-point revisions encode presence separately from the value, so an absent
field and a present null cannot share the same revision.
Protected containing fields, nested ownership,
identity and other admitted views remain protected through alternate lenses.
`protected: ["$value"]` makes the whole value immutable. These rights do not
grant ownership acceptance or permit dropping unknown fields/history.

Native points need no JSON consumer or Work-catalog read permission. Their
bindings address **existing original service interfaces**, for example:

```json
{"native":"branch","id":"EXISTING-BRANCH-ASSOCIATION"}
{"native":"review","component":"EXISTING-ORIGINAL-CONTEXT-KEY"}
{"native":"execution","package":"ADMITTED-PACKAGE","task":"qa-execution"}
```

The point shape stays the same; native `writable` must be empty because native
state cannot be replaced by the file publisher. A packet's logical write-set
still fences native work. Branch/ref changes use the exact original admitted
association/ref adapter. QA uses its original procedure, resources, candidate
export, runner and independent acceptance. Reviews uses its selected original
component, method, collector, context and history. Preparation also runs on the
ordinary Source service path, binding reports to their actual input revision.
Native bindings neither issue those authorities nor manufacture acceptance.

Native `incarnation` must equal the branch association's incarnation, the
review context's original run (handle before a run exists), or the digest of
the execution admission's original receipt string, respectively. `line` remains
a separately selected controller identity. Component keys retain their branch
incarnation meaning; titles, package labels and paths do not supply a line.
Missing/unavailable originals refuse with a specific dependency. Work can
observe a native return only with independently issued current coordination
and every original member/admission check. Other roles retain their own roots
and native authority. No authoritative file projection or shadow native state
is created.

Both file and non-file discovery authorize every native operand before taking
any candidate snapshot or registering a reference/continuation. Exact trusted
permission-index lookups (package, repository operand, admitted roots, component,
collector and current member/coordination authority) precede physical repository,
procedure/tool, ref and history acquisition. A wrong incarnation is no permission
to inspect another scope. Snapshots with an acting job use this same scope gate;
jobless revision observations are controller-side observations of already selected
bindings, not a discovery authorization interface. Original association identity,
method/resource, context/collector/capability and effect checks still follow.
Work reads original Reviews returns through their actual source/member lineage,
through sole Reviews consolidation and later Work continuations. Each edge keeps
its actual collected result/attempt, frozen members, package, hashes, holds and
current authority. Consolidation follows the original native proposer interface;
it does not become that proposer or acquire its execution rights. An unrelated
component name cannot select another context. Effective event or admission-fallback
branch operands receive the same scope gate; logical component-key comparison
does not resolve Git identity. No Work execution scope is inserted upstream.

An addressed input or typed result may contain:

```json
{"integration":{"reads":["Main:related-blockers"],"writes":["Main:work-a"],
                "versions":{"Main:work-a":"SERVICE-VERSION","Main:related-blockers":"SERVICE-VERSION"}}}
```

Versions bind point definition, current values in every selected mirror and a
cooperative service mutation generation. Preparation binds current versions to
the frozen original sources and policy. A stale arriving packet enters local
reconciliation. Already-bound current single packets use direct publication.
Conflicting queued packets form pairs with the same execution package; further
arrivals remain distinct continuations. Related read/write sets, overlapping
selector lenses, branch associations and explicit resources fence concurrent
conflicts. Disjoint point model work can overlap, including within one shared
file. All selected tasks share the explicit model budget; task capacity is at
most five, and QA has at most five executions across tasks. QA same-package
exclusion persists; an unrelated cleanup need not await all QA executions.
Actual ordinary resource leases and continuing branch/reviewer contexts remain
binding. No original attempt, source revision or current verdict is refreshed.

File overlap resolves unique selectors to the actual file and material, so two
different selectors for one record or a parent/child lens conflict. Cooperative
publication records material mutation generations independently of selector
names. A change followed by restoration invalidates an older alias decision.
Native versions retain original histories/turns/executions and possible-effect
intents; native ref/session/resource exclusion includes original unknown turns.
New native effects recheck the prepared read-set before creating their original
intent. Read-only reports keep their original versions so later arrivals
reconcile. This adds neither hostile-writer CAS nor external ABA detection.
Generation/history storage and lookup costs require workload qualification;
this capability supplies no sustained latency or fairness claim.

Missing point metadata selects the central discovery lane. Its separately serialized lane batches new
candidates and supplies the existing admitted point catalog for identity and
relationship discovery. It never creates a readiness gate on anchored work. Other admitted same-task
packages may appear as frozen read-only discovery neighbors; their original
package, admission and processing duty remain separate. Role-to-Work returns
still require their genuine receiving/coordination authority; discovery cannot
borrow cross-role access.
Malformed/unresolved typed bindings retain an operational dependency rather than
silently losing the event or blocking unrelated candidates.
Known existing work with no usable selector can explicitly carry
`integration: {"unresolved_existing": "owned lookup/interface dependency"}`.
It cannot become a duplicate new record. Missing metadata denotes unanchored
input, not proof that the work is new; discovery must resolve that distinction.

`TASK_CONTEXT.local_integration` supplies mode, genuine decision authority,
current basis and the selected method's four steps. Reconciliation and discovery
return `completion.integration_steps`, in order, each with `step` and substantive
`evidence`. These are collected attributed method returns, not software proof of
semantic correctness. User-owned choices remain scope/blocker questions. Broader
concerns use point-specific necessary `required=settled` handoffs, retaining full
source, dissent and actual answer recipient. Methods never gain new authority.

`ownership_fields` names the controller-known acceptance/ownership fields for
its consumer schemas; new records cannot invent those bindings and new point
definitions must protect them. This complete vocabulary also applies inside
new list members and newly added allowed objects on anchored points, including
through alternate views. Built-in ownership names remain protected. Neutral
values and separately named proposal text may be added under genuine write
rights; the spelling of proposal text does not itself establish accepted ownership. Unknown schema meanings remain a qualification
question for actual Work.

Discovery may append new records and propose owners while retaining existing
records/text. It cannot manufacture accepted ownership. If an explicit
`new_point_prefix` is selected, `completion.discovered_points` may propose new
bindings of the same shape under that namespace and an already admitted line.
An empty point catalog can instead start from controller-selected
`discovery_lines: [{"line":"GENUINE-LINE", "incarnation":"GENUINE-LIFECYCLE",
"authority":"ISSUED-NAMESPACE-AUTHORITY-AND-WHY"}]` on the task. No fictitious
record is required. New bindings must match a selected line **and incarnation**.
Publication validates stable unique postimage identities, roots/targets and all
participating task policies before effects. After all duties publish, the service
records the new bindings with original discovery custody and emits separate
version-bound point continuations. Tasks share new points only through an
explicitly common selected prefix. The original discovery source stays held
while those live identities consume its provenance. No whole-catalog migration
or automatic identity retirement is selected.

Non-file discovery may link already existing native identities through the same
namespace/line validation after original completion/effect gates. It creates no
branch, session, execution, acceptance or permission. It emits scoped native
continuations with original sources and collectors. Actual new Work records
still owe all seven file consumers. An unanchored native effect waits for the
scoped continuation; discovery itself cannot bypass original effect admission.

Under the cooperative publication lock, service rebase checks every relevant
read/write version and builds new postimages from **current** peer bytes. It
applies only authorized point changes; Markdown keeps additive supplements with
all existing text intact. Every existing surface remains a consumer/duty.
Separate immutable service stages preserve the model's original proposals and
fresh preimages; the original same-inode publisher still makes backups, intents,
fsyncs and readback receipts. The log uses only its supported bounded observation
and opaque kernel conservation; no full-log Python read/hash is added. Rebase
uses the current bounded log preimage, permitting independently prepared new
entries to conserve each other under the lock.

A completed commit can rejoin already observed receipts without repeating effects,
even after a later disjoint update. A partial/unknown intent refuses replay and
keeps its actual custodian. Multi-file publication is not atomic; noncooperating
writers and same-byte external delete/recreate/ABA are not qualified by these
cooperative versions. Filesystem inode changes and changed bound incarnation
values refuse. Operators must qualify outside writers and authentic lifecycles.

Independent `work_coordination` in a genuine processing selection names
`authority`, exact existing Work `tasks` and upstream `source_roles` (Branch,
QA, Reviews). It does not insert Work into execution admissions. Automatic
Branch/QA admission remains unchanged. A genuine return retains package and all
source members; each member's hash, hold and admitted ancestry is checked.
Work still needs current processing/role/effect authority. Its coordination
neither grants Branch/QA execution roots nor claims native-owner full read.
Published responses and delegated handoffs keep their separate receiving duties.

Oversized typed result objects reaching `Store.collect` retain exact original recovery bytes, witness, blob
custody and collector while their transport remains incomplete. If storage cannot
admit conservation, collection refuses with the original collector still owning
it. Encoding/acquisition can precede the transport bound; no memory bound follows.
No caps increase/refund, birth reset, debt deletion or historical replay occurs.
The AppServer's earlier text-size filter can refuse a final before that collector
path. Exclusive-create/file-journal interruption can also need same-original
manual recovery. Custody and incomplete status remain with that collector; no
universal oversize recovery, automatic overwrite, deletion or replay is promised.
Processing, issue resolution and effect settlement remain distinct. Whole
processing plus 24 hours **and** every hold remains the retirement condition.
Repeated due violations remain distinct notifications; no violation is silent.
The public pool remains hot user-controlled across all five enabled profiles;
no account/private-state probing or fixed-account routing is introduced.

## First ingress: actual owner mapping

An ordinary Board post preserves its SDK text/ref and visible author/recipient;
JSON text, attachment names and point-shaped refs do **not** become integration
metadata. Missing metadata is unresolved, with durable queue responsibility and
an operational dependency. It is not evidence of new work. Fresh Luna LOW
classification and queue commit still precede notification ACK. A mapping hold
leaves unrelated known scopes runnable.

The supported operating interface extends the existing **owner input resolution**
receipt; no new catalog, Store event injection or SQL operation is needed. For an
active original grant, the actual receiving owner uses:

```sh
coordinator --config CONFIG input-show EVENT
coordinator --config CONFIG resolve-input EVENT --receipt RECEIPT.json
```

`CONFIG`, `EVENT` and `RECEIPT.json` are the actual selected configuration, exact
visible source event ID and owner-authored receipt file. The complete receipt
for an already known Work point is shaped as follows (all identities/evidence
must be supplied from actual authority, not copied from this example):

```json
{
  "source_hash":"HASH_RETURNED_BY_INPUT_SHOW",
  "mode":"route", "task":"work-proposer", "package":null,
  "related_event":null, "related_job":null,
  "reason":"Actual original source concerns this existing work and why",
  "evidence":["Actual independent identity/receiver decision reference"],
  "remaining_obligations":[],
  "integration":{"state":"known","reads":["ALREADY-SELECTED-WORK-POINT"],"writes":[]}
}
```

Only the optional `integration` request is new. Its exact alternatives are
`{"state":"known","reads":[...],"writes":[...]}`, `{"state":"new"}` or
`{"state":"unresolved-existing"}`. Known requires a nonempty union of unique,
already permitted point keys. The caller cannot supply `versions`. The service
revalidates each original source/collector/member/hold, current routes and
receiver scope, then observes versions under the cooperative snapshot lock.
The observation is stored in the existing `input_resolutions.prior` as
`integration_observation`; original event bytes/hash and all original members
remain unchanged. This is additive workflow metadata, with existing journal
budgets/correction limits, not a production schema migration.

Resolution requires fresh classification before the same original can reserve.
The mapping is specific to the selected task, policy, admission, grant/enrollment
and processing capability. Changed bindings refuse; versions are never refreshed
by classification or reservation. Stale arrivals enter ordinary reconciliation
at preparation. Existing original anchors and published commit continuations
cannot be retargeted by resolution, even to another permitted point. An already
reserved original cannot be remapped or replayed. Existing owner package binding
remains explicit: Work Board refs do not select packages; any necessary package
route must first use the existing owner resolution against the authentic admitted
package, while retaining the original null package/source bytes.

In a stopped, Work-issued software processing epoch, genuine Work can select
`"input_mappings":["work-proposer","work-integrator","qa-execution"]` in the
processing selection, narrowed to actual already selected local tasks. This
optional allowlist changes no task/point/native/admission/effect rights. It is
compatible with a continuing **future-only** selection: no retained-history
permission is added. Existing capabilities without this explicit selection do
not acquire it automatically. The actual receiving owner then uses:

```sh
coordinator --config CONFIG processing-source CAP EVENT
coordinator --config CONFIG processing-map-input CAP EVENT --receipt RECEIPT.json
```

The same complete receipt above selects the exact original allowed receiver
task/package and typed mapping. The service requires current selected source,
role/point/grant/admission authority and the actual original receiver owner.
Work's selection is not another owner's consent. New independent known inputs
can be mapped under this one current capability while another known scope is
running; no capability rotation, global readiness/window or historical inquiry
is needed for each new mapping. Fresh classification remains owed. A held source
refuses before source-body acquisition by this command. An absent mapping task,
point, package, scope or grant returns to Work as a dependency. Source selection
and actual runtime activation remain the genuine operator's separate effects.

The existing exact `processing-owner-source CAP ROLE resolve-input EVENT` and
`processing-owner-apply CAP --request OWNER-REQUEST.json` path remains available
where Work has separately selected that exact owner operation. A future-only
selection still excludes those historical/exact resolve-input operations; use
its explicitly selected `input_mappings` route for genuinely future inputs.
Processing control workers keep their existing admitted result contract and do
not infer mappings from arbitrary message text.

For a genuine collected response or addressed handoff, map the **actual receiving
event**, after production intake/delivery has conserved it. Internal response
routes remain `responses`; addressed software routes remain the source job's
effective current `software_handoffs` (including its bound prospective epoch).
The original durable Board delivery/receiver intent, original result/attempt,
every frozen member, collection, payload hash and grants are rechecked before
point acquisition. A different recipient/task may choose a different permitted
mapping under its own existing authority. `body.source_result.integration` stays
original evidence; it is never blindly promoted into a receiver anchor. Anchored
internal responses and service commit continuations retain their precedence.

For first QA execution, the real Branch owner must first admit the original exact
package/task/procedure/resources/receipt through the existing owner admission
interface. Select a permitted `native:execution` binding whose incarnation is
`digest(admissions.receipt)` over the stored encoded **string**, not a digest of
the parsed object. Then the actual QA owner resolves its original addressed
Board/received event to that selected point with the known mapping above, using
its admitted package and `qa-execution` task. No response edge to QA is invented:
use genuine addressed Board ingress or an independently selected exact software
handoff route. Missing and explicitly new/unanchored QA inputs cannot reserve an
execution or consume `qa_package_owners`. The original ordinary adapter,
preparation/current-basis checks, leases, independent acceptance and completion
remain necessary after reservation.

Branch and Reviews can select an already accepted `native:branch` association
within their own role/package/read roots. Primary read-only Source can remain
outside `local_integration.tasks` and open its ordinary original root before a
run identity exists. Its genuine collected return then reaches the selected
Reviews integrator; no Source Decide/Act or guessed `native:review` run is needed.
Work reading native returns still needs independently issued Work coordination.
A point mapping grants none of those upstream/native/branch rights.

Only positively identified new candidates enter central discovery, comparing
existing catalog and other new packets before emitting anchored scoped outputs.
The typed new request records the actual owner's reason/evidence; software does
not prove that semantic judgment. Missing/ambiguous existing identity stays
unresolved. Routine file preparation freezes versions with the actual source
snapshot before releasing its cooperative lock or staging; an intervening commit
cannot stamp newer generations onto an older read.
# Prospective automatic metadata lookup (opt-in)

`processing-map-input` / `resolve-input` remain actual-owner bootstrap and
recovery interfaces. Unattended ordinary processing instead needs a genuine
Work-selected `metadata_lookup` in the processing selection. **The following
example is UNSELECTED; source installation does not select any permissions.**

```json
{"metadata_lookup":{
  "tasks":["work-proposer","work-integrator","qa-execution"],
  "authority":"GENUINE WORK MUST SUPPLY the bounded prospective metadata outcome and why",
  "max_points":16,"max_bytes":65536
}}
```

This is separate from `input_mappings` (native receiver owner), general control
disposition, software package admission, independent Work coordination and
ordinary effect authorization. It selects only existing local tasks, their
original roles, routes, roots, grants and package permissions. It applies after
the original processing source-birth boundary, never to an old unknown attempt.
The software actor remains itself. It gets no native-owner receipt, package
consent, assignment/acceptance, native creation, collector or effect authority.

The production tick first obtains fresh Luna LOW classification and a durable
queue responsibility; those precede ACK. An instanced read-only metadata worker
then receives permitted point values and service-observed revisions captured
**before its model read**. It selects known read/write points, positively new
work, or unresolved-existing meaning. The original source/hash, birth, first
ACK and classifier attribution survive. A derived route requires another fresh
LOW classification before reservation. Unknown is never a positive-new signal.
Only positively new business candidates enter central discovery; known work,
including metadata newly indexing an existing item, stays in local/pairwise
reconciliation with scoped outputs. Unrelated known scopes progress in parallel.

Existing selected points can be looked up without additional config. To index
existing identities that appear later inside an explicitly bounded namespace,
a task may select `lookup_scopes`. This example is also **UNSELECTED**:

```json
{"lookup_scopes":[{
  "prefix":"known-main:","member_field":"id",
  "point":{"kind":"item","line":"Main","incarnation":"CHOSEN DELIVERY LIFETIME",
    "bindings":[{"target":"/OWNED/EXAMPLE/catalog.json","path":["items"]}],
    "resources":[],"protected":["id","owner","accepted_owner"],"writable":["state"]}
}]}
```

One exact file target/parent selector per template is supported. A list requires
the explicitly selected unique string `member_field`; a dictionary requires
`member_field:null` and uses exact existing keys. The service derives child
selectors and keys from observed existing material. It never creates a work
item, infers novelty from a title or accepts ownership. Template protection,
writable fields, delivery line/incarnation and actual receiver access are
preserved. Limits refuse oversized contexts as owned scope questions. The
snapshot is bounded by the selected byte/point limits as well as ordinary
journal/attempt/window budgets; those are not a sustained latency guarantee.

For large selected list parents, opt in to **`"query":true` on that file
template**. This is a protocol choice, **UNSELECTED** until Work selects the
actual future configuration and delegation. It requires a nonempty stable
`member_field`; it does not enumerate mixed dictionary roots as business items.
An optional `view:["field","nested_field"]` appends that exact object-key path
after the resolved member selector. This is an explicit field lens, not silent
evidence truncation. Presence and JSON null remain different. Scalar writes
still need `$value` authority; ancestor identity/ownership/protection cannot be
escaped by selecting a narrower lens. Native templates have no file views.

The production protocol for a query scope is:

1. Fresh LOW and durable queue responsibility precede ACK, as above. A separate
   `input-locator` attempt receives the original source and selected template
   descriptions, **without backing-file acquisition**. It returns only
   `{hints:{task:{scope_digest:[stable_member_strings]}}}` in `decision_json`.
   Each string is the raw `member_field` value. The template `prefix` decorates
   generated point keys, not member values; the service never strips prefixes
   or translates unknown aliases into members.
   A hint is not a work proposal, existence/absence finding, revision, novelty
   decision or permission. It may name a specifically source-related existing
   work/relationship view; it may not send a whole catalog to a model.
2. Complete original locator collection binds the worker/controller, current
   capability, source hash, exact task/template policy and no-tool result.
   Unknown, malformed, failed or uncollected results stay owned, without replay.
   Hints outside the selected scopes refuse. Missing hints never mean new work.
3. On a later normal tick, the service revalidates the original source and
   current bindings, acquires only the selected permitted backing files, and
   resolves hinted members uniquely. Their values/absence and versions are a
   **new observation before the semantic metadata model reads/decides**. An
   absent/ambiguous member has no point and is retained in `unresolved` with
   its scope, exact hint and status. Other uniquely matched members progress
   without requiring unrelated rows to have valid or unique identities.
   Unresolved relationships survive in the snapshot, frozen resolution and a
   once-only attributed Work question created before semantic interpretation,
   including when that original later fails or known members are mapped. They cannot
   authorize new business. A solely ambiguous member remains unresolved; no
   title or alias chooses an owner or row. Earlier model
   reads receive no new current stamp. Semantic interpretation remains the
   existing known / positively-new / unresolved-existing protocol.
4. Fresh derived LOW precedes task reservation. Actual proposal preparation
   supplies bounded `observed_values` and versions for its selected points.
   Changed material reconciles with the earlier mapping revision; the earlier
   resolution/ACK/source/birth is retained unchanged.

`processing-source CAPABILITY EVENT --diagnostics` exposes only the exact
current prospective source: original locator and mapping collection metadata,
hint presence/count, unresolved relationships, source-bound observation/mapping
dependency, reservation and task attempt start/collection. The dependency is
kept separately from later generic reservation errors. No raw model result,
prompt, native session, backing values or old-source inventory is returned.
Collection, mapping, reservation, task start and acceptance remain distinct;
these diagnostics never assert whole processing or genuine acceptance.

`max_bytes` continues to bound metadata model context, not whole source-file
size. Backing acquisition uses the existing artifact ceiling (default 32 MiB,
also bounded by journal byte capacity), cumulatively across selected files for
one observation. No context cap is raised and no shadow catalog is persisted.
Projection and prepared-task contexts still refuse over their selected/result

File acquisition/parsing and original publication snapshots/stages still cost
