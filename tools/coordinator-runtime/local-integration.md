# Continuous point integration

This source capability retains the existing file consumers, seven Work duties,
review/QA/CI/acceptance/risk gates and original collectors. It establishes no live
adoption, policy ownership, model efficacy, latency or receiving qualification.

A controller selects `local_integration` explicitly in configuration. Existing
unselected journals/tasks retain their historical contracts. The supported
current-configuration draft accepts it as an explicit
`prospective_scope_selection.local_integration` option; every affected task must
be in the prospective task selection. It cannot change task effects, execution
admission, owners, roots, routes or canonical targets. Actual Work must select
current genuine point/resource/owner bindings and routine decision authority
before deployment. No example here is an operating configuration.

```json
{
  "max_inflight": 8,
  "tasks": {
    "work-integrator": {
      "capacity": 4,
      "discovery_batch": 8,
      "points": ["Main:work-a", "Main:related-blockers"],
      "authority": "GENUINELY ISSUED bounded routine allocation authority and why",
      "method": "/fictional/selected-four-step-method.md",
      "new_point_prefix": "Main:new:",
      "ownership_fields": ["owner", "ownership_acceptance"]
    }
  },
  "points": {
    "Main:work-a": {
      "kind": "item", "line": "Main", "incarnation": "controller-bound-lifecycle",
      "bindings": [{"target": "/fictional/ASSIGNMENTS.json",
                    "path": ["assignments", {"field": "work_id", "value": "WORK-A"}]}],
      "resources": ["fictional-owner-session"],
      "protected": ["work_id", "owner", "ownership_acceptance", "history", "sources"],
      "writable": ["state", "next_action", "current_view"]
    },
    "Main:related-blockers": {
      "kind": "relation", "line": "Main", "incarnation": "controller-bound-relation-set",
      "bindings": [{"target": "/fictional/REGISTER.json", "path": ["work_a_blockers"]}],
      "resources": [], "protected": [], "writable": []
    }
  }
}
```

Use stable object keys or unique array field/value selectors, never array/line
indices. A point can bind multiple JSON consumer locations. `line` and
`incarnation` are genuine controller bindings, not model ownership claims.
Relevant relation sets, absence predicates and shared invariants are separate
read points. Select all actual dependencies; software does not discover hidden
semantic invariants from JSON leaves. Writable fields bound service changes;
unknown fields, protected ownership/identity fields and prior array members
remain conserved. Reassignment/acceptance needs separate real authority, not a
local model statement. Main and Cloud/PR1230 require distinct genuine bindings.

Scalar and list points use an explicit `writable: ["$value"]` for whole-value
changes. An empty writable list permits no change. Value types stay fixed;
changing a schema needs a separate authority decision. Prior list members,
including duplicates, survive with their JSON types recursively intact. A boolean
member cannot be spent as an integer (including inside arrays/objects); matching
consumes one occurrence, and genuinely new members may still append. The same
typed comparison guards protected views, write-sets and current-byte reuse.
Object field rights also conserve presence: an absent unselected or protected
field cannot be created as JSON null. Explicit null remains valid in selected
ordinary fields and neutral/proposal additions within their actual rights.
File-point revisions encode presence separately from the value, so an absent
field and a present null cannot share the same revision.
Protected containing fields, nested ownership,
identity and other admitted views remain protected through alternate lenses.
`protected: ["$value"]` makes the whole value immutable. These rights do not
grant ownership acceptance or permit dropping unknown fields/history.

Native points need no JSON consumer or Work-catalog read permission. Their
bindings address **existing original service interfaces**, for example:

```json
{"native":"branch","id":"EXISTING-BRANCH-ASSOCIATION"}
{"native":"review","component":"EXISTING-ORIGINAL-CONTEXT-KEY"}
{"native":"execution","package":"ADMITTED-PACKAGE","task":"qa-execution"}
```

The point shape stays the same; native `writable` must be empty because native
state cannot be replaced by the file publisher. A packet's logical write-set
still fences native work. Branch/ref changes use the exact original admitted
association/ref adapter. QA uses its original procedure, resources, candidate
export, runner and independent acceptance. Reviews uses its selected original
component, method, collector, context and history. Preparation also runs on the
ordinary Source service path, binding reports to their actual input revision.
Native bindings neither issue those authorities nor manufacture acceptance.

Native `incarnation` must equal the branch association's incarnation, the
review context's original run (handle before a run exists), or the digest of
the execution admission's original receipt string, respectively. `line` remains
a separately selected controller identity. Component keys retain their branch
incarnation meaning; titles, package labels and paths do not supply a line.
Missing/unavailable originals refuse with a specific dependency. Work can
observe a native return only with independently issued current coordination
and every original member/admission check. Other roles retain their own roots
and native authority. No authoritative file projection or shadow native state
is created.

Both file and non-file discovery authorize every native operand before taking
any candidate snapshot or registering a reference/continuation. Exact trusted
permission-index lookups (package, repository operand, admitted roots, component,
collector and current member/coordination authority) precede physical repository,
procedure/tool, ref and history acquisition. A wrong incarnation is no permission
to inspect another scope. Snapshots with an acting job use this same scope gate;
jobless revision observations are controller-side observations of already selected
bindings, not a discovery authorization interface. Original association identity,
method/resource, context/collector/capability and effect checks still follow.
Work reads original Reviews returns through their actual source/member lineage,
through sole Reviews consolidation and later Work continuations. Each edge keeps
its actual collected result/attempt, frozen members, package, hashes, holds and
current authority. Consolidation follows the original native proposer interface;
it does not become that proposer or acquire its execution rights. An unrelated
component name cannot select another context. Effective event or admission-fallback
branch operands receive the same scope gate; logical component-key comparison
does not resolve Git identity. No Work execution scope is inserted upstream.

An addressed input or typed result may contain:

```json
{"integration":{"reads":["Main:related-blockers"],"writes":["Main:work-a"],
                "versions":{"Main:work-a":"SERVICE-VERSION","Main:related-blockers":"SERVICE-VERSION"}}}
```

Versions bind point definition, current values in every selected mirror and a
cooperative service mutation generation. Preparation binds current versions to
the frozen original sources and policy. A stale arriving packet enters local
reconciliation. Already-bound current single packets use direct publication.
Conflicting queued packets form pairs with the same execution package; further
arrivals remain distinct continuations. Related read/write sets, overlapping
selector lenses, branch associations and explicit resources fence concurrent
conflicts. Disjoint point model work can overlap, including within one shared
file. All selected tasks share the explicit model budget; task capacity is at
most five, and QA has at most five executions across tasks. QA same-package
exclusion persists; an unrelated cleanup need not await all QA executions.
Actual ordinary resource leases and continuing branch/reviewer contexts remain
binding. No original attempt, source revision or current verdict is refreshed.

File overlap resolves unique selectors to the actual file and material, so two
different selectors for one record or a parent/child lens conflict. Cooperative
publication records material mutation generations independently of selector
names. A change followed by restoration invalidates an older alias decision.
Native versions retain original histories/turns/executions and possible-effect
intents; native ref/session/resource exclusion includes original unknown turns.
New native effects recheck the prepared read-set before creating their original
intent. Read-only reports keep their original versions so later arrivals
reconcile. This adds neither hostile-writer CAS nor external ABA detection.
Generation/history storage and lookup costs require workload qualification;
this capability supplies no sustained latency or fairness claim.

Missing point metadata selects the central discovery lane. Its separately serialized lane batches new
candidates and supplies the existing admitted point catalog for identity and
relationship discovery. It never creates a readiness gate on anchored work. Other admitted same-task
packages may appear as frozen read-only discovery neighbors; their original
package, admission and processing duty remain separate. Role-to-Work returns
still require their genuine receiving/coordination authority; discovery cannot
borrow cross-role access.
Malformed/unresolved typed bindings retain an operational dependency rather than
silently losing the event or blocking unrelated candidates.
Known existing work with no usable selector can explicitly carry
`integration: {"unresolved_existing": "owned lookup/interface dependency"}`.
It cannot become a duplicate new record. Missing metadata denotes unanchored
input, not proof that the work is new; discovery must resolve that distinction.

`TASK_CONTEXT.local_integration` supplies mode, genuine decision authority,
current basis and the selected method's four steps. Reconciliation and discovery
return `completion.integration_steps`, in order, each with `step` and substantive
`evidence`. These are collected attributed method returns, not software proof of
semantic correctness. User-owned choices remain scope/blocker questions. Broader
concerns use point-specific necessary `required=settled` handoffs, retaining full
source, dissent and actual answer recipient. Methods never gain new authority.

`ownership_fields` names the controller-known acceptance/ownership fields for
its consumer schemas; new records cannot invent those bindings and new point
definitions must protect them. This complete vocabulary also applies inside
new list members and newly added allowed objects on anchored points, including
through alternate views. Built-in ownership names remain protected. Neutral
values and separately named proposal text may be added under genuine write
rights; the spelling of proposal text does not itself establish accepted ownership. Unknown schema meanings remain a qualification
question for actual Work.

Discovery may append new records and propose owners while retaining existing
records/text. It cannot manufacture accepted ownership. If an explicit
`new_point_prefix` is selected, `completion.discovered_points` may propose new
bindings of the same shape under that namespace and an already admitted line.
An empty point catalog can instead start from controller-selected
`discovery_lines: [{"line":"GENUINE-LINE", "incarnation":"GENUINE-LIFECYCLE",
"authority":"ISSUED-NAMESPACE-AUTHORITY-AND-WHY"}]` on the task. No fictitious
record is required. New bindings must match a selected line **and incarnation**.
Publication validates stable unique postimage identities, roots/targets and all
participating task policies before effects. After all duties publish, the service
records the new bindings with original discovery custody and emits separate
version-bound point continuations. Tasks share new points only through an
explicitly common selected prefix. The original discovery source stays held
while those live identities consume its provenance. No whole-catalog migration
or automatic identity retirement is selected.

Non-file discovery may link already existing native identities through the same
namespace/line validation after original completion/effect gates. It creates no
branch, session, execution, acceptance or permission. It emits scoped native
continuations with original sources and collectors. Actual new Work records
still owe all seven file consumers. An unanchored native effect waits for the
scoped continuation; discovery itself cannot bypass original effect admission.

Under the cooperative publication lock, service rebase checks every relevant
read/write version and builds new postimages from **current** peer bytes. It
applies only authorized point changes; Markdown keeps additive supplements with
all existing text intact. Every existing surface remains a consumer/duty.
Separate immutable service stages preserve the model's original proposals and
fresh preimages; the original same-inode publisher still makes backups, intents,
fsyncs and readback receipts. The log uses only its supported bounded observation
and opaque kernel conservation; no full-log Python read/hash is added. Rebase
uses the current bounded log preimage, permitting independently prepared new
entries to conserve each other under the lock.

A completed commit can rejoin already observed receipts without repeating effects,
even after a later disjoint update. A partial/unknown intent refuses replay and
keeps its actual custodian. Multi-file publication is not atomic; noncooperating
writers and same-byte external delete/recreate/ABA are not qualified by these
cooperative versions. Filesystem inode changes and changed bound incarnation
values refuse. Operators must qualify outside writers and authentic lifecycles.

Independent `work_coordination` in a genuine processing selection names
`authority`, exact existing Work `tasks` and upstream `source_roles` (Branch,
QA, Reviews). It does not insert Work into execution admissions. Automatic
Branch/QA admission remains unchanged. A genuine return retains package and all
source members; each member's hash, hold and admitted ancestry is checked.
Work still needs current processing/role/effect authority. Its coordination
neither grants Branch/QA execution roots nor claims native-owner full read.
Published responses and delegated handoffs keep their separate receiving duties.

Oversized typed result objects reaching `Store.collect` retain exact original recovery bytes, witness, blob
custody and collector while their transport remains incomplete. If storage cannot
admit conservation, collection refuses with the original collector still owning
it. Encoding/acquisition can precede the transport bound; no memory bound follows.
No caps increase/refund, birth reset, debt deletion or historical replay occurs.
The AppServer's earlier text-size filter can refuse a final before that collector
path. Exclusive-create/file-journal interruption can also need same-original
manual recovery. Custody and incomplete status remain with that collector; no
universal oversize recovery, automatic overwrite, deletion or replay is promised.
Processing, issue resolution and effect settlement remain distinct. Whole
processing plus 24 hours **and** every hold remains the retirement condition.
Repeated due violations remain distinct notifications; no violation is silent.
The public pool remains hot user-controlled across all five enabled profiles;
no account/private-state probing or fixed-account routing is introduced.
